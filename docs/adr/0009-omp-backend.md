# 0009 omp 作为可选后端

在 opencode 之外新增 omp 作为可选后端（见 `CONTEXT.md`「后端」），两者并存、配置 `backend` 选定、默认 opencode；选定后端不可用时直接报错，不自动退到另一个后端——两边 agent 与模型配置不同，悄悄换后端产出的候选会让人困惑。生成调用收进 `Backend` 接口：冷启动/常驻、会话 id 从哪抓、何为会话失效都由后端自己决定，generate.rs 只保留「失效则清会话重试一次」的共享逻辑（ADR-0007），以及「新建会话却没拿到 id 时在 stderr 提示常驻会话没建立」——两个后端抓 id 的方式不同，提示放在这一处两边才一致。接口的会话入参分三种用法而非一个可选 id：一次性（`reuse_session=false`）、新建并带回 id、续接已有 id——只给可选 id 分不清前两者，而它们在两个后端里走的路径不同（opencode 的 default/json 格式，omp 的 `--no-session` 与落盘新 id）。状态文件 `server.json` 按后端分开存，切回原后端会话还能续上；文件读不出（损坏或顶层不是对象）时，改写前先挪到 `server.json.corrupt`（已有就依次试 `.corrupt.1`、`.corrupt.2`…，用第一个空闲名，旧备份不覆盖）并在 stderr 提示实际备份路径，不悄悄连带清掉其他后端的分区；旧格式（顶层 `{url, pid, session_id}`）读作 opencode 分区、下次写入转成新格式，升级不丢常驻会话；`reset-session` 只清当前后端分区里的会话；`model` 只留一个字段，由当前后端解释，空则用后端自己的默认。

omp 后端与 opencode 有三处刻意不对称。其一，只走冷启动 `omp --mode json`、`resident` 对它不生效：omp 没有可共享的 HTTP 服务，`--mode rpc` 只活在 stdio 父进程里，要复用得自己写守护进程，而它冷启动自身开销约 1.5s，不值得。其二，常驻会话按目录各存一个（`{cwd → session_id}`，会话放在 ask-opencode 自己的 `--session-dir`，即配置目录下的 `omp-sessions/`：这些会话带着 cmd-gen 系统提示与快照，混进用户日常的 omp 会话列表只会添乱）：omp 续接会话会把进程切回会话创建时的目录，全局一个会话会让只读侦查跑在旧目录里。目录取 `$PWD` 逻辑路径、不做 realpath，与用户在 shell 里看到的目录一致；会话 id 取 NDJSON 首行 session header，续接用 `--resume <完整 id>`，退出码 1 且 stderr 含 `Session "<id>" not found.` 视为会话失效。其三，omp 没有主会话 `--agent`，cmd-gen 正文编进二进制、经 `--system-prompt` 传入，与 opencode 的 agent 文件共用同一份正文。

只读侦查在 omp 下必须与 opencode 同样严格，最终机制（omp 18.8.6 实测）是四件套：`--no-skills --no-rules --no-extensions` 收窄注入；`--tools bash` 让内置工具只剩 bash，对齐 cmd-gen agent 的 `"*": deny`；`--approval-mode always-ask` 让所有非 read 档工具在无 UI 时直接失败——MCP 工具不受 `--tools` 约束、默认按 exec 档处理，写文件与 eval 同理，这一层把它们都挡住；`--config` 叠加文件给 bash 白名单与上下文屏蔽。白名单由 build.rs 从 cmd-gen agent frontmatter 逐条抽出，两个后端共用一份。两个后端的 `*` 都能跨参数、空格和引号匹配，带 `*` 的前缀规则等于不约束参数，所以白名单只收窄 allow（例如 `git branch` 只列不带 `*` 的只读写法、不放行 `find`），收窄不了的危险参数才用 deny 例外：`git *--output*` 挡 diff 类命令写文件，`*>*` 挡重定向（opencode 1.18.35 不检查重定向，引号里带 `>` 的只读命令一并被拒，可以接受）。两个后端都是 deny 优先，但冲突时取哪条相反：opencode 以最后命中的规则为准，omp 以首条命中为准。所以 frontmatter 里 deny 一律写在 allow 后面，build.rs 抽规则时再把 deny 稳定挪到 allow 前面（相对顺序不变）供 omp 使用——规则顺序由这一步编译期换序保证，不靠写 frontmatter 的人记得两套语义。omp 叠加末尾再补 `{"match": "*", "approval": "deny"}`：omp 未命中默认放行，少了兜底就等于没有白名单；白名单的 allow 在 always-ask 下仍生效（bash 对命中 allow 的命令自报 `policy: allow`，先于档位比较），所以不必退回按服务器名写 `disabledExtensions`。allow 规则不放行带管道、`;`、`&&` 等控制符的命令，叠加里同时钉死 `bash.allowCompoundCommands: false`，免得用户配置把它打开。用户级上下文默认会进 omp 的系统提示（`~/.omp/agent/AGENTS.md`，以及用户显式启用的 claude/codex/gemini/copilot 等来源），叠加用 `disabledExtensions` 按 `context-file:user:<文件名>` 屏蔽 AGENTS.md、CLAUDE.md、GEMINI.md、copilot-instructions.md，项目级保留。叠加文件以 JSON 写到状态文件同目录的 `omp-readonly.json`，先写临时文件再改名，并发的 shell 不会读到半截。已知残留：用户自己在配置里写了 `tools.approval.<工具>: allow` 的，该工具会越过 always-ask，这算用户的显式授权，不做对抗；MCP 服务器照常拉起、工具定义照常进上下文，只是调用不了；叠加里的 `disabledExtensions` 是数组、会整个替换用户的同名配置，用户禁用的 MCP 服务器在这次调用里也会被拉起，同样调用不了。
